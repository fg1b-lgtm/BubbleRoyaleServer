# 2026-08-28 (D-10 + D-9) — select, IOCP, 세션 생명주기

**1. 오늘 하려던 것**

오전에 `select` 로 다중 접속을 만들어 논블로킹 개념을 익히고,
오후에 IOCP 로 전환한다. 완료 포트 하나, 워커 스레드 하나, `WSARecv` 한 바퀴.

완료 조건은 두 개였다.
IOCP 로 에코가 동작할 것. 그리고 `OVERLAPPED` 가 왜 필요한지 코드 없이 말로 설명할 것.

둘 다 통과했다. 클라이언트 두 개를 동시에 붙여서 양쪽 다 답을 받는 것을 확인했다.
어제는 두 번째가 답을 못 받던 자리다.

시간이 남아서 8/29 분량인 세션 생명주기까지 했다.
`WSASend` 로 바꾸고, `OVERLAPPED` 확장 구조체로 Recv 와 Send 완료를 구분하고,
참조 카운트로 언제 지울지를 정했다.
정상 종료와 강제 종료 둘 다 `closing` 다음에 `fully closed` 가 찍히는 것을 확인했다.

**2. AI에게 물은 것 / 어떻게 물었나**

1단계로 완성 코드를 받되 줄마다 왜 그렇게 쓰는지를 붙여달라고 했다.

IOCP 코드를 다 치고 나서도 전체적인 코드 흐름이 눈에 안들어와서 "이 세부 동작 하나하나 순서랑 의미가 이해가 안 된다." 라고 물었다.
그러니까 손님 한 명이 접속해서 끊을 때까지를 시간 순으로 풀어줬다.
어느 스레드가 어디서 자고 있고 언제 깨는지가 그때 보였다.

헷갈린 걸 직접 짚어서도 물었다.
"`PostRecv` 가 등록이고 `WorkerThread` 가 주문인가. `WorkerThread` 는 언제 실행되나.
주문 들어오면 실행이면 `PostRecv` 안에 그 호출이 있어야 하는데 없다."
이름표가 반대였다. `PostRecv` 가 주문이고 등록은 `CreateIoCompletionPort` 한 줄이다.
`WorkerThread` 는 `CreateThread` 한 줄에서 시작해서 계속 돌고 있었다.
`PostRecv` 가 부르는 게 아니라 둘이 완료 포트를 사이에 두고 간접적으로만 이어져 있다.

세션까지 하고 나서는 코드가 아니라 방법을 물었다.
"이걸 코드로 짤 때 무슨 생각을 하면서 짜야 하나. 실제로 고치거나 늘릴 때는 어떤 순서로 생각하나."

답은 이랬다. 함수부터 짜지 않는다.

1. 무엇이 언제까지 살아야 하나 (수명) → 수명이 같은 것끼리 묶으면 그게 구조체다
2. 누가 만들고 누가 지우나 (소유)
3. 무슨 일이 일어날 수 있나 (사건 목록) → 이 목록이 그대로 분기가 된다
4. 각 사건마다 그다음 뭘 걸어야 하나 (상태 전이)
5. 마지막에 실패 경로를 채운다

`Session` 과 `IoContext` 가 이 순서로 나온 것이었다.
먼저 만들어놓고 뭘 넣을까 고민한 게 아니라, 수명이 같은 것을 묶은 결과였다.

**3. AI가 틀린 것 / 내가 어떻게 잡았나**

- AI가 준 세션 코드에 이중 해제가 있었다.
  `main` 에서 첫 `PostRecv` 가 실패하면 `closesocket` 하고 `delete` 하는 코드였는데,
  `PostRecv` 안에서 실패하면 `Release` 가 이미 닫고 지운 뒤였다.
  `AddRef` 로 1이 됐다가 실패해서 `Release` 로 0이 되면 그 안에서 `delete` 까지 한다.
  같은 걸 두 번 지우는 거라 죽거나, 안 죽고 나중에 엉뚱한 데서 터진다.
  접속하자마자 바로 끊는 클라이언트가 정확히 이 경로를 밟는데,
  오늘 완료 조건이 클라 10개를 랜덤하게 끊는 거라서 바로 걸릴 자리였다.
  이건 내가 먼저 못 봤다. AI가 먼저 찾았다.
  다만 오늘 배운 원칙을 적용하면 걸러지는 종류였다.
  누가 만들고 누가 지우는지가 정해져 있으면 둘이 같이 지울 수가 없다.

- 구술 테스트에서 `OVERLAPPED` 를 지역 변수로 만들면 왜 안 되냐는 질문에
  쓰레기가 쌓여서 느려진다고 답했다. 방향이 반대였다.
  지역 변수는 오히려 저절로 사라지는 게 문제다.
  주문은 끝났지만 작업은 진행 중이라, 운영체제가 아직 그 주소에 쓰고 있는데
  그 자리가 없어진다. 남의 자리에 덮어쓰게 된다.
  코드는 다 쳤고 돌아갔는데 코드를 안 보고 물으니 반대로 답했다.

- 세션 코드를 다 치고 나서 파악이 안 됐다.
  코드에 적힌 순서와 실제 도는 순서가 뒤죽박죽이고, 변수와 함수가 너무 많았다.
  이유가 있었다. C++ 은 쓰기 전에 먼저 선언해야 해서 파일이 실행 순서의 반대로 적힌다.
  그래서 맨 아래 `main` 부터 거꾸로 올라가며 읽어야 한다.
  그리고 함수 일곱 개를 다 볼 필요가 없었다.
  `main` 의 `while` 과 `WorkerThread` 의 `while` 두 군데만 보고,
  나머지는 이름만 믿고 넘어가는 게 맞는 읽는 방법이었다.

**내가 만든 버그**

`select` 에서 `continue` 가드 조건을 둘 다 뒤집어 썼다.

```cpp
if (s != INVALID_SOCKET) continue;      // 살아 있으면 건너뛴다
if (FD_ISSET(s, &read_set)) continue;   // 울렸으면 건너뛴다
```

진짜 손님은 전부 건너뛰고 빈 자리에만 `recv` 를 걸었다.
빈 자리에는 소켓이 아니라 `INVALID_SOCKET` 이 들어 있어서 `10038` 이 났다.
그리고 진짜 손님은 처리를 못 받으니 데이터가 계속 남아 `select` 가 즉시 돌아오기만 했다.
6초에 1704만 줄을 찍었다.

`continue` 는 건너뛴다는 뜻이니 조건 칸에 쓸 것은 처리할 조건이 아니라 건너뛸 조건이다.

**확인해둔 것**

같은 `Client.exe` 하나로 서버 네 개에 다 붙었다.
어제 blocking, 오늘 `select`, IOCP, 세션. 클라이언트는 한 글자도 안 고쳤다.

IOCP 는 프로토콜이 아니라 I/O 모델이다.
내 프로그램이 어떻게 기다리느냐의 문제라 나만 고치면 된다.
